# 如何写好 Git 提交信息

> 提交信息很重要。本文告诉你如何写得好。
>
> *参考：[Chris Beams — How to Write a Git Commit Message](https://chris.beams.io/git-commit)*

随便打开一个 Git 仓库的提交日志，你很可能会看到一片混乱：

```bash
$ git log --oneline -5 --author cbeams --before "Fri Mar 26 2009"

e5f4b49 Re-adding ConfigurationPostProcessorTests after its brief removal in...
2db0f12 fixed two build-breaking issues: + reverted ClassMetadataReading...
147709f Tweaks to package-info.java files
22b25e0 Consolidated Util and MutableAnnotationUtils classes into existing AsmUtils
7f96f57 polishing
```

而维护得好的仓库，提交记录是简洁一致的：

```bash
$ git log --oneline -5 --author pwebb --before "Sat Aug 30 2014"

5ba3db6 Fix failing CompositePropertySourceTests
84564a0 Rework @PropertySource early parsing logic
e142fd1 Add tests for ImportSelector meta-data
887815f Update docbook dependency and generate epub
ac8326d Polish mockito usage
```

`git diff` 能告诉你**改了什么**，只有提交信息能告诉你**为什么改**。一条提交信息就能看出一个开发者是不是好的协作者。下面是社区早已形成共识的七条规则。

## 写好提交信息的七条规则

### 1. 用空行分隔标题和正文

> 最好以一行简短（少于 50 个字符）的文字概括改动，然后空一行，再写更详细的描述。第一个空行之前的文本被当作提交标题，该标题会在整个 Git 中被使用。

**并非每次提交都需要正文。** 改动足够简单时，一行就够了：

```
Fix typo in introduction to user guide
```

需要更多解释时，再写正文：

```
Derezz the master control program

MCP turned out to be evil and had become intent on world domination.
This commit throws Tron's disc into MCP (causing its deresolution)
and turns it back into a chess game.
```

有了标题与正文的分离，`git log --oneline` 和 `git shortlog` 才能正常工作：

```bash
$ git shortlog
Kevin Flynn (1):
      Derezz the master control program

Alan Bradley (1):
      Introduce security program "Tron"

Ed Dillinger (3):
      Rename chess program to "MCP"
      Modify chess program
      Upgrade chess program
```

> ⚠️ 没有空行分隔，这些工具的显示就会乱掉。

### 2. 标题行不超过 50 个字符

50 个字符不是硬性限制，而是经验法则。保持这个长度能确保标题易读，也迫使你把改动用最简洁的方式说清楚。

> 💡 如果你很难写出简洁的标题，很可能说明一次提交了太多改动，请尽量做**原子性提交**。

GitHub 的 UI 完全遵守这个约定——超过 50 字符会警告，超过 72 字符会用省略号截断。**把 50 当作目标，72 当作硬上限。**

### 3. 标题行首字母大写

✅ 正确：

```
Accelerate to 88 miles per hour
```

❌ 错误：

```
accelerate to 88 miles per hour
```

### 4. 标题行不要以句号结尾

✅ 正确：

```
Open the pod bay doors
```

❌ 错误：

```
Open the pod bay doors.
```

### 5. 标题行使用祈使语气

**祈使语气**指像在发号施令一样写作，例如 `Clean your room`、`Close the door`、`Take out the trash`。

Git 本身在自动创建提交时用的就是祈使语气：

```bash
# git merge 自动生成的提交信息：
Merge branch 'myfeature'

# git revert 自动生成的提交信息：
Revert "Add the thing with the stuff"
```

用祈使语气，你就是和 Git 自身保持一致。

| ✅ 正确的祈使语气 | ❌ 错误的陈述语气 |
|---|---|
| `Refactor subsystem X for readability` | `Fixed bug with Y` |
| `Update getting started documentation` | `Changing behavior of X` |
| `Remove deprecated methods` | `More fixes for broken stuff` |
| `Release version 1.0.0` | `Sweet new API methods` |

**一个简单的检验方法：** 一条格式正确的提交标题，应该总能完整地填入下面这句话：

> **If applied, this commit will \_\_\_\_\_\_\_\_\_\_**

- ✅ If applied, this commit will **refactor subsystem X for readability**
- ✅ If applied, this commit will **remove deprecated methods**
- ❌ If applied, this commit will **fixed bug with Y**
- ❌ If applied, this commit will **more fixes for broken stuff**

> 📌 祈使语气只对**标题行**重要，写正文时可以放松。

### 6. 正文每行不超过 72 个字符

Git 不会自动换行，写正文时必须手动注意右边距。建议在 72 个字符处换行，这样 Git 有足够的缩进空间，整体仍能保持在 80 字符以内。

### 7. 正文解释"是什么"和"为什么"，而非"怎么做"

来看 Bitcoin Core 的[经典提交](https://github.com/bitcoin/bitcoin/commit/eb0b56b19017ab5c16c745e6da39c53126924ed6)：

```
Simplify serialize.h's exception handling

Remove the 'state' and 'exceptmask' from serialize.h's stream
implementations, as well as related methods.

As exceptmask always included 'failbit', and setstate was always
called with bits = failbit, all it did was immediately raise an
exception. Get rid of those variables, and replace the setstate
with direct exception throwing (which also removes some dead
code).

As a result, good() is never reached after a failure (there are
only 2 calls, one of which is in tests), and can just be replaced
by !eof().

fail(), clear(n) and exceptions() are just never called. Delete
them.
```

- **代码本身能说明"怎么做"**——如果代码太复杂需要额外解释，应该写在源代码注释里。
- **提交信息应该关注"为什么"**——改动前的工作方式（有什么问题）、改动后的工作方式，以及为什么选择这种方法。

> 那个感谢你的未来维护者，很可能就是你自己。

## 标准模板

综合以上七条规则，一个标准的提交信息长这样：

```
用 50 个字符左右的文字概括改动

更详细的解释性文字，如有必要的话。每行控制在 72
个字符左右。在某些上下文中，第一行被视为提交标题，
其余文本被视为正文。分隔标题和正文的空行至关重要
（除非你完全省略正文）；如果你把它们连在一起，
`log`、`shortlog` 和 `rebase` 等工具会出问题。

解释这个提交要解决的问题。重点放在你为什么要做
这个改动，而非怎么做的（代码已经说明了怎么做）。

这个改动有什么副作用或其他非直觉的后果？这里
就是解释的地方。

空行后再起一段。

 - 也可以用列表的形式

 - 通常用连字符或星号作为列表标记，前面加一个空格，
   列表项之间用空行分隔，不过具体写法因人而异

如果你使用问题追踪系统，可以在底部引用：

Resolves: #123
See also: #456, #789
```

## 实用建议

**拥抱命令行，离开 IDE。** 用 `git commit`（不加 `-m`）打开你熟悉的文本编辑器来写提交信息，远比在 IDE 的小输入框里写要好。

**关于团队约定。** 一个团队在开始协作之前，至少应就三点达成共识：

1. **风格**：标记语法、换行边距、语法、大小写、标点符号
2. **内容**：正文中应该（和不应该）包含什么信息
3. **元数据**：如何引用 Issue ID、Pull Request 编号等

## 总结

| 规则 | 说明 |
|---|---|
| 1. 空行分隔 | 标题与正文之间必须有空行 |
| 2. 标题 ≤ 50 字符 | 目标是 50，上限是 72 |
| 3. 标题首字母大写 | `Fix bug` 而非 `fix bug` |
| 4. 标题不加句号 | 不需要 `。` 或 `.` |
| 5. 标题用祈使语气 | `Add feature` 而非 `Added feature` |
| 6. 正文 ≤ 72 字符/行 | 手动换行，给 Git 留缩进空间 |
| 7. 正文写为什么 | 不要解释代码本身，解释决策的原因 |

> 好的提交信息不是一蹴而就的，它始于刻意练习，终于习惯成自然。下一次 `git commit` 时，试试这七条规则吧。
