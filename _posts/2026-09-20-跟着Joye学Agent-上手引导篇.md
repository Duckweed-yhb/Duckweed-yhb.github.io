# Agent 入门该学什么：读 Joye 的 Agent 工程师入门指南

## 前言

本文整理自 Joye 的[《写给所有“想入门 Agent 但不知道从哪开始”的人》](https://www.joyehuang.me/blog/20260517---agentonboardingguide/post)——2026-05-17 首次发布，2026-07-25 更新到 v1.2，全文约 1.85 万字。

作者自述：墨尔本大学计算与软件工程在读，在上海一家独角兽公司做 Agent 全栈开发实习，日常就是这份文档里写的东西——Harness、上下文工程、工具调用、Eval；2025 年底到 2026 年初密集面过 100+ 家 AI 公司的 Agent 相关岗位，拿到 30+ 个 offer，那段经历写成了本系列的前两篇（[面试修炼手册](/2026/09/20/跟着Joye学Agent-面试篇/)、[模拟面试复盘](/2026/09/20/Agent工程师模拟面试/)）。

这篇文章的自我定位很明确：**它给你的是地图，不是腿。** 读完它你还不会写 Agent，但你会知道这个领域长什么样、接下来 1–2 个月按什么顺序学什么。作者给每一步都写了“验收标准”，用来检验自己是不是真的在走。

下面是按 v1.2 主线做的条理化整理；模型版本号、跑分这类最容易过期的内容我没有抄录，需要时请以原文和厂商官网为准。

## 一、这份材料是什么、不是什么

**它写给两类人**：完全没有编程或 LLM 背景的人（需要一张“地图”看全貌）；有一定编程基础但没真正接触过 LLM 应用的人（需要一份“对照表”，把已经会的东西和新方向之间的桥搭起来）。

**读完它你应该能**：用三句话讲清 Agent 和普通 LLM 应用的区别；知道接下来 1–2 个月按什么顺序学什么；听到行话不再发懵；以及**不再焦虑**——知道这条路有方向、可以走，现在出发并不晚。

**它不是什么**（预期对齐）：

- 不是代码教程——不会有大段 Python / TypeScript 代码
- 不是框架手册——不会逐条讲 LangChain / Vercel AI SDK 的 API
- 不是论文综述——不会推 Transformer 公式、不带读论文

**怎么用**：第一遍按顺序通读建立轮廓，第二遍回到最有共鸣的章节细读。作者反复强调一句话——**只读不动手是这个领域最大的坑。**

## 二、认识 Agent：一个定义、三个误解、四件套

**定义**：如果说 LLM 是一颗“大脑”，Agent 就是这颗大脑加上了眼睛、手、记忆，以及一个能让它自己循环工作的身体。更严谨的说法是——**以 LLM 为决策核心、能够感知环境、调用工具，并通过循环完成多步任务的系统**；很多 Agent 还会维护任务状态或跨会话记忆。

**三个常见误解**：

| 误解 | 澄清 |
|---|---|
| Agent ≠ 聊天机器人 | 聊天机器人的核心是“对话”，Agent 的核心是“完成任务”，对话只是它接收任务的一种方式 |
| Agent ≠ 单次 LLM API 调用 | 单轮调用是“输入 → 输出”，没有循环、工具、状态；“循环 + 工具”凑齐才谈得上 Agent |
| Agent ≠ 用 LLM 包装的表单 App | 真正的 Agent 要让模型有“自己决定下一步做什么”的空间，而不是按人类预设流程走完 |

作者补了一句很关键的话：**“自主程度”是一个旋钮，不是资格考试。** 真实生产系统里最常见的形态，是确定性工作流做主干、LLM 只在分类、规划、选工具这些节点上做局部决策——很多可靠的 Agent，恰恰是故意调低模型自由度换来的。所以别把“全自主循环”当正统、把工作流当伪 Agent。

另外要分清：今天 ChatGPT / Claude / Gemini 网页端内置的联网搜索、代码执行、文件读写，是**厂商在产品层把 Agent 能力打包好给用户用了**，而不是“LLM 本身变成了 Agent”——你要学的是外面那一整套工程。

**四件套**：

- **大脑（LLM）**：思考与决策。它是四件套里唯一你没法自己做的一件——**所以 Agent 开发，做的其实是“模型以外的一切”**，业内把这套外围工程统称为 **Harness**：记忆、工具、循环、上下文管理、可靠性兜底
- **记忆（Memory）**：短期记忆是当前任务的上下文，长期记忆是跨会话的持久信息；工程实现上再细分为 Working / Short-term / Long-term 三层
- **手（Tools / Function Calling / MCP）**：搜索引擎、代码执行、邮件 API、数据库查询都是工具；第三方工具的标准化接入方式是 MCP
- **循环（Agent Loop）**：`感知 → 思考 → 行动 → 感知 → …`，最经典的实现是 ReAct；终止条件通常是模型自判完成 / 达到最大步数 / 用户中断

“Agent 开发 = 做 Harness”不是一句修辞，它**有实测支撑**：Databricks 在千万行代码库上的内部评测显示，同一个模型、同样的思考强度，只换一个 harness，部分任务的单次成本相差超过 2 倍，而完成质量基本一致——差别来自各家管理上下文的方式不同。**同一颗大脑，Harness 决定了它被用得好不好。**

**一个最小工作流**（原文以 Coding Agent 为例）：“把所有旧的 `logV1()` 换成 `logV2()`，跑通测试。”它内部大致跑五轮：grep 找到 37 处调用 → 批量替换（其中一处因写法变体失败，模型读到失败信息后换更宽松的匹配重试）→ 发现上下文里没有测试工具，于是 `tool_search("run tests")` 按需加载 → 测试挂了 3 个，读报错后发现参数顺序变了，回去修正 → 汇报结果。

五个值得记住的关键点：

1. **下一步动作主要由模型动态选择**——在运行时允许的边界内，它判断要不要调工具、调哪个、是否重试、何时完成；权限、审批、最大步数和停止规则仍由系统控制
2. **工具执行不是模型在做**——模型只是输出“我想调这个工具”，真正执行是你的程序；这也正是安全边界所在
3. **失败是主路径，不是异常路径**——一个只演示“一路成功”的 Demo 和生产级 Agent 之间，差的就是这些
4. **工具不是全量塞给模型的**——`tool_search` 是“搜索工具的工具”，工具库可以上百个，模型平时只看到核心几个
5. **记忆贯穿整个流程**——修 bug 时模型还记得最初任务与第一轮找到的位置

## 三、生态地图：五层名词一次铺平

原文用五层来组织术语（作者声明这是**帮助记忆的地图、不是严谨的架构分层**）：

| 层 | 关键词 | 这一层要搞清的事 |
|---|---|---|
| 模型层 | Claude / GPT / Gemini / Qwen / DeepSeek / Kimi / GLM / MiniMax | 分海外闭源与国内开源两个池；**优先记定位，而不是记版本号**（版本号和跑分是最易过期的内容） |
| 框架层 | 官方 SDK vs 第三方框架 | 第一个 Agent 建议用轻抽象的 SDK，而不是重型框架 |
| 协议层 | MCP、Skills、Function Calling / Tool Use | 工具的“接口标准化”与“能力打包”是两件事 |
| 数据层 | RAG、Memory、LLM Wiki、Agentic Retrieval | RAG 正在部分退潮，但远没死——要看具体条件 |
| 应用层 | AI 搜索、Chat-to-BI、Vibe Coding | 当下被反复提及、跑通商业化的三个方向 |

**模型层**的三条选型建议：不是越大越好，**按任务分级使用**（简单意图识别、路由用便宜小模型，复杂推理才用旗舰）；大部分国内模型提供 OpenAI 兼容端点，同一套代码改 `base_url` 就能切换；**不要押宝单一模型**，成熟项目会同时接 2–3 家按任务路由。

**框架层**：官方 SDK（OpenAI / Anthropic / Google）最稳定，但覆盖面各异；第三方里作者最推荐入门用 **Vercel AI SDK**——它不限模型（换模型只改一个 import），而且**它只是一个 SDK、不是框架**，给的是流式输出、工具调用、结构化输出这些原语，不强制你按它的抽象组织代码，对想看清“Agent Loop 到底在做什么”的人很友好。LangChain / LangGraph 生态最大，但抽象最重，**不建议作为第一站**。

**协议层**：**MCP**（Model Context Protocol）是 Anthropic 2024 年底推出的开放协议，可以理解成 Agent 领域的“USB 标准”——以前每接一个工具都要自己写适配，现在有了统一对话方式；它已是事实标准。**Skills** 则是把“一组专门的工具 + 精心调过的 Prompt 指导 + 示例与参考 + 必要的代码片段”打包成一个可加载、可复用、可版本化的能力模块（通常是一个含 `SKILL.md` 的文件夹）。它解决的核心问题是**按需暴露**：接 50 个工具模型极容易选错，但分组装进 10 个 Skills，模型只在匹配场景才看到对应工具。**MCP 解决“工具如何被调用”，Skills 解决“工具如何被组织和触发”，两者互补**，一个 Skill 内部可以调用多个 MCP Server。顺带澄清：Function Calling 与 Tool Use 说的是同一件事，只是两家叫法不同。

**数据层**：这一层变化最快。传统 RAG 的假设是“上下文小、token 贵”，而今天长上下文已到百万级，对很多场景来说“先检索再生成”的复杂管道**根本没必要**——Karpathy 推广的 **LLM Wiki** 思路是：对个人/小团队的中等规模知识库，直接用 Markdown 组织成维基结构，按需把相关章节塞进上下文，没有切片误差、没有召回率问题、调试简单、还更容易命中 Prefix Cache。**但 RAG 没死**，以下情况通常仍更值得优先评估检索方案：语料规模很大或更新频繁；查询高度局部、要求精确引用与证据回溯；延迟和 token 成本敏感；权限粒度细（检索层可以先按权限过滤）。作者特别提醒：**隐私和多租户本身并不决定是否用 RAG**——三种方案都可以本地部署，也都必须单独做好身份、权限与数据隔离。至于 **Memory**，它和 RAG 有重叠但不同，更强调“对当前用户/会话的个性化记忆”；**Agentic Retrieval / Agentic Memory** 则是 2025–2026 的新趋势——检索不再是被动管道，而是 Agent 自己决定要不要搜、搜什么、结果要不要再提炼。

（v1.2 相对早期版本还更新了这些：MCP 已捐入 Agentic AI Foundation、Skills 成为开放标准并出现供应链风险、新增若干官方 Agent SDK。）

## 四、趋势、心态与避雷

**“晚不晚”是一个伪命题。** 作者的标准回答是：**这条赛道上“老人”也才两三年经验。** 时间线很简单——2022 年 11 月 ChatGPT 发布；2023 年初 AutoGPT 兴起、6 月 OpenAI 推出 Function Calling；2024 年 Cursor 商业化爆发、年底 Anthropic 推出 MCP；2025 年 Manus、Claude Code 等产品集中爆发，年底 MCP 捐入基金会、Agent Skills 成为开放标准。也就是说，今天入门的你，三年后也是“老人”。

**为什么是现在**，三个判断：① Agent 正在从“Demo 期”走向“生产期”，可靠性、可观测性、Eval、成本控制这些工业级问题被认真对待——**这是工程师真正能发挥价值的阶段**；② 基础设施层的标准化窗口期还在，你**有机会参与到一个新行业基础设施的建设里**；③ 人才需求在系统性增长，2026 年起国内头部大厂开始成体系地开 Agent 工程师岗。原文还引用了一个第三方信号：Y Combinator W26 批次里约 41.5% 的公司被归为 Agent 基础设施——作者自己也提醒，这是第三方的划分口径，只宜当趋势信号，不宜当精确统计。

**不需要焦虑的四条理由**：行业没有绝对权威（OpenAI、Anthropic 的最佳实践都是工程师边做边写，差距是实践积累不是天赋）；公开资料空前丰富，但生产数据、内部评测和真实故障经验仍构成信息差；工具门槛的“简单部分”在下降、“深的部分”在上升；**对手不是别人，是去年没动手的你自己。**

第三点展开说就是全文最锋利的一句判断：**当造一个“没有壁垒的 Agent 项目”变得很简单时，没有壁垒的项目本身就不值钱了。** GitHub 上一千个“AI 健康助手”，面试官扫一眼就知道含金量。真正的门槛被推到了更深的位置——**这不是“门槛下降”，而是“门槛从代码能力转移到思考深度”。**

**六个常见误区**：我数学不好搞不了 AI（你做的是应用不是算法）；要先学完 LLM 原理（应用层与算法层是两条相对独立的赛道）；学这个要会很多框架（框架是工具不是目标）；没大厂背景找不到工作（这个方向恰是创业公司的天下）；学这么快会不会过时（表层工具在变，ReAct、上下文工程、记忆系统、工具调用、Eval 这些核心问题反复出现在不同产品里）；Agent 是不是红海了（多数领域仍在寻找可靠产品形态与商业模式，竞争真实存在，但区分度来自场景、数据、可靠性和落地能力）。

## 五、怎么入门：用 → 懂 → 造

**前置技能比想象中短。** 第一步不是挑语言、配环境，而是**先装上一个 Coding Agent**（Claude Code / Codex）——它在整条路线里扮演四个角色：老师、工具、教材，以及最后你项目的对照组。语言只要 Python 或 TypeScript 任一；不需要先学的清单包括深度学习数学、PyTorch/模型训练/微调、Transformer 内部细节、以及各种 Agent 框架 API。最先要练的是三个动作——**读**（AI 写的代码能看出大概在做什么）、**问**（看不懂就追问到能用自己的话复述）、**判断**（跑挂了能把报错丢回去，修完知道怎么验证真的好了）。同时给自己设一条最低工程能力线：变量与函数、JSON、HTTP、环境变量、Git 基本操作、日志、依赖管理和测试——不用先背完再开始，但项目结束时应该能解释它们在系统里做什么。

**第一跳：用（3–7 天）——先成为 Agent 的重度用户。** 有条件把同一个任务交给两个 Coding Agent，比较它们拆任务、用工具、处理失败的方式。这一跳要拿到两样东西：**边界感**（它什么任务一把过、什么任务会自信地给你错误答案、多长的任务会迷失——读十篇测评都读不出来），以及**让它产出工程级代码的手艺**：在项目里放 `CLAUDE.md` / `AGENTS.md` 写清技术栈与禁区；把任务拆小、说清（“帮我做个网站”和“给这个页面加一个带防抖的搜索框，复用现有 Input 组件”得到的是两种东西）；要求它自证（跑测试、跑 lint、自己验证）；**每次改动都读 diff**——这既是质检，也是零基础的人学代码最快的路径。

> 验收标准：能具体讲出它三次失败的样子；项目里有一份自己写的 `CLAUDE.md` / `AGENTS.md`，并且能说出加它前后输出质量的差别。

**第二跳：懂（1–2 周）——从用户变成拆解者。** 你每天在用的这个东西本身就是很直观的教材。做两件事：**拆解手里的 Agent**（它什么时候决定调工具、工具失败后做了什么、长任务里怎么压缩上下文——先看 trace、工具调用记录和 diff，再问它“你刚才为什么先跑测试再改代码”，但要注意**事后解释不一定忠实反映内部推理，要以可观察的执行记录为准**）；**让 AI 带你复现一个最小 Agent**（让它写十行以内代码把“你好”发给一个便宜的 LLM API 并逐行讲解，再把“扩成多轮对话”“加一个搜索工具”留成作业，你来改、它来 review——**代码由它起草，理解和验证由你负责**）。

> 验收标准：能对着 SDK 代码指出 Agent Loop 每一步对应哪个关键点；画得出你的 Coding Agent 完成一次任务的时序；最小 Agent 有一份失败案例清单，每条都能说出对应哪类问题。

**第三跳：造（1–2 个月）——做一个跨得过灵魂拷问的真实项目。** 选题从你自己的重复劳动里挖，不要做“通用问答助手”。判断够不够格，现在是**双重灵魂拷问**：① 用豆包 / ChatGPT 直接就能解决，为什么要做这个？② 2026 年的升级版：**用 Claude Code 装个 Skill 就能解决，为什么要做这个？**——你的对照组已经不是聊天框，而是一个通用 Agent。

这两个问题不用凭空想，**直接把想法丢给 Coding Agent 让它当场试**：如果它二十分钟就覆盖了核心价值，继续追问你在可靠性、专有数据、持续运行、用户体验或领域约束上增加了什么；它卡住的地方，往往就是值得深入的项目空间。原文给了一个升级示例：**“每周帮我摘要 Newsletter”** 一句话就能被通用 Agent 干掉，不够格；但**“接上我的私有阅读源，记住我每次点‘没兴趣’之后越推越准，每周一早上自动跑好等我醒来”**——私有数据、长期记忆、长驻运行三个卡点全占，这才有了壁垒。**同一个题材，壁垒从来不在功能本身，在通用 Agent 够不着的那几厘米。**

> 验收标准：项目部署在别人能访问到的地方；有真实用户用过（哪怕只有你室友）；复盘博客或完整 README 写完。

## 六、求职准备：把项目“讲到极致”

如果只能把准备时间花在一件事上，就是把项目讲到极致——说清四件事：**做了什么**（背景、你的角色、整体架构）、**为什么这么做**（每个关键决策的依据）、**踩过什么坑**（失败案例 + 解决方案）、**学到了什么**（重做你会怎么改）。

原文给了一个可以当模板的正例（数字是为演示叙事结构设定的示例）：

> “我做了一个 Newsletter Agent。第一版每周把 30 多封邮件全文塞给旗舰模型做摘要，单次成本 4 块多，而且长上下文里它经常漏掉我真正关心的内容。我改成两级：先用便宜模型按历史反馈给每封邮件打分预筛，只有前 10 封进旗舰模型深度摘要——成本降到 8 毛。但预筛带来新问题：偶尔把感兴趣的邮件筛掉了。我给预筛加了两条硬规则：点过“没兴趣”的来源降权、点开读完过的来源永远直进精选，把“漏掉重要内容”从每周两三次压到基本为零。最后加了个每周自动跑的 Eval：拿上周真实点击当标准答案回测预筛准确率，低于 85% 就提醒我调整。”

这段话里有**指标（成本 4 块 → 8 毛、漏检两三次 → 0）+ 决策（模型分级 + 反馈规则）+ 权衡（成本 vs 漏检）+ Eval（用真实行为回测）**——顺便展示了模型分级、成本控制和 Eval，全是面试官想追问的钩子。

简历层面三个要点：不要只堆技术名词；每段项目按“问题 — 方案 — 结果”结构；尽量给可复现的指标，估算的要注明样本、口径与估算方式。面试层面考的是“你经历过什么”，四个维度：基础认知、系统设计、工程取舍、行业认知——**第一层靠经验、第二层靠理解、第三层靠判断、第四层靠 taste 和阅读量，越往后越能拉开差距。**

**六个不要走的弯路**：一上来就啃 LangChain 源码；过早卷模型微调；追新框架不沉淀基本功；看完教程就觉得自己会了；只做不沉淀（至少留下 README、架构图、指标口径和失败复盘）；**把 Coding Agent 用成黑盒——或者反过来拒绝用它**（只复制粘贴从不读 diff，用得越久越空心；坚持全手写，速度和视野又跟不上）。

## 七、第五层：八件内功

原文最后一章是给“做完第一个项目、想知道再往深走是什么”的人。v1.2 把它从六件扩到八件，并按“做对 / 扛得住 / 可判断”三类收束：

| 内功 | 一句话理解 | 关键决策点 |
|---|---|---|
| 上下文工程 | 在有限空间里把最该被看到的信息以最有效方式呈现 | 结构化 Prompt；关键信息前置/后置（Lost in the Middle）；历史摘要替代历史明文；Prefix Cache 友好的排列 |
| 记忆系统 | 让 Agent 像人一样分层记事 | 写入策略（什么值得记）、读取策略（何时/如何检索）、遗忘策略（过时与矛盾的记忆要清理或衰减） |
| 工具调用 | 让 Agent 能“动手”，并且不要乱来 | Tool Schema 写得越清楚越不容易用错；工具数量上限约 10 个，超出要做工具路由；重试要有上限与幂等；**事前约束优于事后兜底** |
| 可靠性 | 从确定性思维切换到概率性思维 | 概率性系统“测过一次就 OK”行不通；结构化输出 + Schema 校验；状态机 + Checkpoint；降级策略 |
| 安全 | v1.2 新增，把散在各章的安全内容收拢成完整一节 | 执行层保护（沙箱、审批）、不可信内容的隔离 |
| 成本控制 | 钱是真的会烧的 | Prefix Cache 友好设计（命中折扣可观）；模型分级；减少 Agent step 数；上下文剪枝 |
| 观测与调试 | v1.2 新增：trace / trajectory / transcript 其实是同一件事 | 一条执行记录该留什么，以及它和 Eval 的分工 |
| 评估（Eval） | Agent 没有“对错”，只有“好坏” | 离线评估、在线评估、LLM as a Judge、A/B 对照；**没有 Eval 的 Agent 优化都是玄学** |

v1.2 还补了两处很实操的细节：成本一节加入了对 Prefix Cache 的复盘——**什么会让缓存悄悄失效，以及“上下文剪枝”和缓存之间的取舍**；Eval 一节补上了 **LLM as a Judge 的自家模型偏好问题**，并强调 judge 要交叉评、且要和干活的模型**分开固定参数**。

此外 v1.2 单独加了一节 **多 Agent**，补上第四章承诺过“面试会考”但正文一直没讲的部分——如果关心这类面试题怎么答，可以回到本系列的[模拟面试复盘](/2026/09/20/Agent工程师模拟面试/)一起看。
