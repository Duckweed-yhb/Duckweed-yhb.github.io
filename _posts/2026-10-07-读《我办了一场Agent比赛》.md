# 为什么不用 Claude Code：读 Joye 的 Summer of Agents 复盘

## 前言

本文整理自 Joye 在 2026-10-06 发布的[《我办了一场 Agent 比赛：评完十几个作品，我们反复在问同一个问题》](https://www.joyehuang.me/blog/20261006---soareview/post)。

背景：Joye 在自己的八百人 QQ 粉丝群（平时聊 AI 和 Agent）发起了一场叫 **Summer of Agents** 的比赛——自由组队，花一个暑假做一个 Agent 项目，最后上台展示。报名的有 45 组，提交企划的不多，加上一拖再拖，他原本做好了「半小时就冷场收尾」的准备。结果 10 月 4 日晚上，十几组同学轮流在飞书会议共享屏幕，每组 5 分钟展示、再回答评委 3 到 5 个问题，从八点不到一直聊到十一点多。

十几个作品评下来，几乎每个都被问到同一个问题的某个版本：

> 那为什么不直接用 Claude Code 或者 Codex？

正如 Joye 所说，它不只是问参赛者的——**每个在做 Agent 产品的人，都值得想一想。**

以下按原文脉络条理化整理，观点与细节归原作者。

---

## 一、获奖作品一览

| 奖项 | 作品 | 一句话 |
|---|---|---|
| 第一名 | Shiori Agent（windy） | 以角色为核心的个人 Agent：角色卡导入、记忆面板、语音、主动聊天、插件系统都做出来了，还能把角色拉进群里一起聊；作者已靠它找到了工作 |
| 第二名 | Speech Agent（猪鼻星） | 把你说过的话变成字幕，再由你挑出值得长期记住的内容，通过 MCP 只读地分享给其他 AI |
| 第三名 | Legion（在希） | 多 Agent 管理系统：一个 Manager 拆任务，分给最多 64 个 Codex 子 Agent 并行执行，再统一验收，在硬件设计和算子优化任务上跑出了实打实的提升 |
| 最佳 Demo 奖 | Obsidian Third Brain | Obsidian 笔记关联插件；不讲项目技术，只看 5 分钟里的表达、展示和问答，当晚全场最佳 |
| 鼓励奖 | 明账 AI 记账、人事 Excel Agent | 临时加的奖：一个是 2026 级新生（当晚年纪最小）做的 Windows 记账工具；一个是工作两三年、非科班、五六月才开始学编程的同学手写代码做的 |

获奖之外，原文真正值得反复读的是那晚聊到的几个问题。下面逐条整理。

---

## 二、绕不开的问题：为什么不直接用 Claude Code

这是当晚出现次数最多的问题。对一个记忆系统项目，Joye 的追问一步步收紧：Codex 和 Claude Code 是当之无愧的 T0 级 Agent，虽然为 Coding 而生但越来越通用，你承认吧？它们从配置到发出第一个 prompt 的上手门槛比你的产品低，你也承认吧？那用户为什么要用你的产品？

2026 年，用户手里已经有一个足够强、门槛足够低的通用 Agent。RSS 摘要、读其他会话的历史、学一个新领域，很多功能让 Codex 起一个定时任务就能做到七八成。所以问题从「我能不能做出来」变成了「**为什么不是它来做**」。

当晚大家给出的、站得住的回答大致有三种：

**1. 把独特的能力做成插件，接进头部 Agent。** 做陌生领域知识地图的那组，被问到平时学新东西时用不用自己的项目，作者坦白还没用过——这很正常，换成谁大概都会直接打开 ChatGPT。反过来想：如果你在某个垂类上真有独特的能力，就把它做成 Skill 或 MCP，接进 Claude Code 和 Codex 里。这还有一个常被忽略的好处：**曝光**——头部 Agent 的用户每天都在增长，接在上面的东西天然能被更多人看到。

**2. 给出一个通用 Agent 不适合做的具体理由。** 问明账作者：你自己就在用 Hermes 这类个人 Agent，为什么不把记账做成它的一个子功能？先说的隐私理由经不起推敲——只要接外部 AI 服务，数据总会离开本机，存在自己电脑上和存在自己服务器上差别没有想象中大。第二个理由就很有说服力：**Hermes 太重，而明账更接近一个记账 App，不是一个 Agent**。作者的习惯也正好是隔一段时间集中导一次账单，在电脑上批量整理，自己保管账本。理由越具体，越站得住。

**3. 大方承认它是一个自己用的项目。** 这完全没问题。降星驰的原话：「我对个人项目和但凡有商业化想法的项目，要求是不一样的。」个人开源项目做到五百、一千个 star 是很有希望的。与其在音乐版权上找卖点（做本地播放器那组），不如把力气花在 Agent 真正擅长的地方：不知道歌名、也记不起歌词，只能用感觉描述一首歌时，传统平台很难搜到——如果它能做好这件事，就是真正的亮点。

### 能用 Hook 解决的，先别做 Harness

第三名的 Legion 是被问得最多的作品。降星驰问了一个很现实的问题：模型迭代一轮，就会把很多 Skill、甚至 Harness 淘汰掉，你怎么保证自己不被淘汰？

例子是现成的：Superpowers 这类流程型 Skill，在模型还比较弱的时候几乎人人都装，新一代模型出来以后用的人就少了很多。「能开 64 个子 Agent」本身也不太构成差异——Codex 的子 Agent 数量改一下配置就能调上去。

Joye 给的建议是一个从轻到重的顺序：

| 层级 | 形态 | 说明 |
|---|---|---|
| 最轻 | Hook | 在 Agent 运行的固定时机自动执行一段脚本，适合处理规则性的约束 |
| ↓ | Skill | 给 Agent 一个额外的专家技能包，本质上是一份按需加载的提示词 |
| ↓ | MCP | 把需要真实执行的能力做成接口，各家 Agent 都能调用 |
| ↓ | Plugin | 把 Skill、MCP、Hook 打包在一起，方便分发和安装 |
| ↓ | Mod | Claude Code 前阵子刚推出的形式，可以直接加面板、状态栏这类界面 |
| 最重 | 独立 Harness 或产品 | 最后才考虑 |

能用前一种解决，就先别跳到后一种——每往后走一步，要维护的东西就多一层，被模型更新覆盖的风险也大一层。现在 Claude 这一类模型差不多一个月就迭代一次。一个三个月后可能被模型自带能力覆盖的独立 Harness，和一个三个月后仍然能被各家 Agent 调用的 Skill，价值差得很远。

所以对 Legion，Joye 最想知道的是：这套分工和验收的规则，能不能先做成 Skill 加 Hook？降星驰也补了一句：Claude Code 和 Codex 都有 Hook，要先证明 Skill 加 Hook 解决不了，才需要一个独立的系统。

顺带的求职建议：**别拿 Coding Agent 或 Harness 当面试项目**——多 Agent 编排的复杂度不亚于分布式系统，面试官会问的，正是上面这些问题。

### 让 Agent 也能用上你的产品

接进头部 Agent 还有另一面：不只是把你的能力接进去，也可以是让 Agent 能用你的产品。

做记忆系统的参赛者被问到「你的产品对 Agent 友好吗」，回答是设计时完全没考虑过——这在记忆和知识库项目里很常见。但群里 bot 的数量越来越多，很快会比真人还多；已经有人在把网页一键转 Markdown，目的就是让 Agent 能更好地读。

所以值得问自己：**你的产品产出的东西，能不能被别的 Agent 低成本地读取、调用、写入？** 一个结构化的输出、一个 MCP 接口，可能比一个漂亮的看板更能让你成为别人工作流里的一环。

---

## 三、一句话介绍产品，比想象中难

降星驰几乎对每个人都问了同样的问题：如果只给你一句话，加一张宣传图，你怎么介绍你的产品？

大家答得都很吃力。「一个套了角色扮演皮的个人 Agent，主要提供情绪价值」「一个让你看到曾经没注意到、但有用的内容的工具」——听起来更像功能描述，还不像别人愿意转述的一句话。这题本来就难，经典产品的口号往往只是一个很短的词组，背后是反复打磨的结果。

它的价值不在文案本身，而在逼你回答几件事：**用户是谁，解决什么问题，和别人差在哪。** 答不上来的时候，往往说明这几件事还没想清楚。

最佳 Demo 奖的 Obsidian 插件就是个好例子。作者讲得自信又流畅，但聊着聊着，发现产品里藏着一个小矛盾：出发点是「用户记了几千条笔记，但不会回去翻」，用法却是「点进某一条笔记，看看它关联了哪些旧笔记」——如果用户本来就不会回去翻，这个入口就不太成立。换一条主线：创作一个新主题时，不知道这个朦胧的想法该打什么标签，也想不起它和哪些旧笔记有关，这才是我真正需要 AI 帮忙的地方。

> 讲得好和想得清是两件事。表达是一个放大器，它放大的是你已经想清楚的那部分。

原文给了两个最简单的检验：

**第一，你自己在用吗？** 连续用超过三天了吗？测试不算。能回答「在用」的项目，后面的问题都答得更有底气。反过来，作者自己都不用的项目，别人也不知道该从哪里问起。

**第二，在你出现之前，有没有人在用很别扭的办法满足这个需求？** 例子是外卖：美团出现之前就有肯德基宅急送，有商家接电话、自己派人送餐——效率很低，但需求真实存在。「只要做得足够方便，就会有人来用」这个逻辑不太成立，因为任何东西都可以这么说。真正重要的需求，哪怕很不方便，也会有人想办法满足。

想知道目标用户的痛点也不用闷在家里猜：群里八百人，发个十块钱红包都会有二十个人认真回答你。红包不是重点，重点是**用户离你很近，可以直接去问。**

## 四、先找到裁判，再堆 token

回到 Legion。被问到和别人的差异在哪时，作者讲到了验收层：不是让另一个 LLM 判断做得对不对，而是接一个外部的验证程序——电子设计里专用的验证工具、算子的性能评测。分数上去就保留，没上去就淘汰，再分配、再迭代，一轮一轮往上爬。

Joye 的第一反应是：那不就是测试吗？复盘时他才意识到，这恰好是 Legion 做对的地方：**它最有价值的部分，不是能开 64 个子 Agent，而是它选的任务有裁判。**

这也解释了为什么 Coding Agent 最先成熟：代码有测试，测试就是裁判。有了裁判，才能放心地堆 token、堆并发，让 Agent 自己往上爬。算子优化、硬件设计、形式化证明，都属于这一类。

没有现成裁判的领域，就要先找一个：

- 数学建模的结果没有绝对的对错——但比赛本身就是裁判，能拿奖就行；
- AI 自动整理的知识库对不对、笔记关联得准不准——没有裁判。能当裁判的只有人，而人恰恰是那个「不会回去看」的角色。

所以动手之前，可以先问自己一句：**谁来判断它做得好不好？** 答案可以是测试、比赛成绩、用户付费，也可以是你自己连续在用。想不出裁判的时候，先别急着堆 Agent。

---

## 五、懂业务的人，正在变得更值钱

当晚让 Joye 印象最深的，是拿鼓励奖的那位人事管理同学：毕业两三年、做人事管理、不是计算机专业，五月底看了他的视频，就想自己做一个 Agent 试试，代码大部分是自己手写的。项目把算工资、汇总各部门表格的工作拆成了几个原子工具：读 Excel、写 Excel、把员工信息表转成数据库、查询员工数据库。

作者说了一句很认同的话：

> 想在工作上用好 AI，其实还是需要对自己的工作有非常足够的了解。

最早的版本是一个把所有表头写死的专用工具，能用，但完全不通用；后来才意识到要把工作步骤原子化。这件事技术上并不难，难的是你得知道这份工作里，哪些步骤可以拆开。

这也是那晚反复聊到的观点：**做 Agent，产品能力比技术能力重要得多。** 以前当然也是这样，但现在多了一个原因：Agent 是一个增量市场，而技术本身在 AI 面前正在贬值，对业务的理解不会。技术选择要有自己的理由，而不是「AI 告诉我用这个」或者「我第一个知道的就是这个」。

Joye 的鼓励是：想做好 Agent 开发，先试着当一个 **Agent 产品经理**——至少深度体验过 20 个 Agent 产品，而且不能只用 Coding Agent。

---

## 写在最后

这大概是「跟着 Joye 学 Agent」系列里最「产品向」的一篇。前几篇讲面试、讲上手，这篇讲的是**做完一个 Agent 之后，怎么被市场接受**：为什么通用 Agent 会是你最大的对手、怎么先接进去再说、为什么先有裁判才能堆 token、为什么懂业务比懂技术更值钱。

我自己记下的几条：

- 「越通用的需求，越是模型的主场；越具体的需求，越是个人开发者的机会」——选赛道的直接标准；
- 「先找到裁判，再堆 token」——任何 Agent 项目立项时都可以先问：谁来判断它做得好不好；
- 一句话介绍 + 两个检验（自己在用吗、之前有没有别扭的替代品）——最简单的产品自检清单。
