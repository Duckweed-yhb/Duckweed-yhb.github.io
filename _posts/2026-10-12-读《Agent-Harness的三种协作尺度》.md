# 哪些会被模型学走，哪些会越做越大：读 Joye 的 Agent Harness 三种协作尺度

## 前言

本文整理自 Joye 在 2026-09-20 发布的[《Agent Harness 的三种协作尺度：哪些会被模型学走，哪些会越做越大》](https://www.joyehuang.me/blog/20260912---codexharnessevolution/post)。

起因是 The Pragmatic Engineer 的一期播客：主持人 Gergely 问 Codex 负责人 Tibo Sottiaux——早期的 Codex 改完代码不会主动跑测试，几个月之后它自己会跑了，你们改的是提示词，还是模型？

Tibo 的回答大意是：Harness（围绕模型做的那部分工程）总是比模型领先一点。模型其实有这个能力，只是还不够稳定，他们就先在外面加一句提醒；等下一代模型训练出来，它自己就会了，这句提醒也就可以删掉。时间一长，他们写给模型的说明越来越短，Harness 也越来越小。

Gergely 的感慨是：作为开发者，这听起来有点泄气——今天认真做出来的东西，下一版模型自己就会了。

Joye 认同这个现象，但结论不同：Tibo 站在 Codex 核心 runtime 的位置上，看到 Harness 在变小；他站在「人和 Agent 怎么一起把事做完」的位置上，看到的是它一直在变大。**两个观察都成立，只是看的不是同一样东西。**

这也是 Joye 在《Personal Agent 拆解》里引用的那篇"讲 Harness 的文章"。以下按原文脉络条理化整理，观点与细节归原作者。

---

## 一、Harness 到底指什么

Joye 习惯把 Agent 拆成四个部分：**大脑（模型）、记忆、工具、循环**。大脑是唯一一个不需要做、也没有能力做的部分——决定不了模型，只能决定调用哪一个；除此之外的全部工作都在模型外面。

模型外面的这一整圈，业内叫 Harness。LangChain 的 Vivek Trivedy 有个很干脆的说法：Agent = 模型 + Harness，模型之外的一切都是 Harness。

这个说法好记，但按位置定义，说不出 Harness 是干什么的，而且什么都装得进去。Joye 更愿意按作用定义：

> **Harness 是让人和 Agent 能够持续协作的一套机制：把人的意图、上下文和规则接到 Agent 的行动上，再把 Agent 做出来的结果交回人的工作流程。**

它是人和 Agent 之间的一座桥——但"桥"只适合解释，正式点叫机制：它不只是把两头连起来，还要管桥上的事——什么可以过、谁来放行、过到一半断了怎么办。

按这个定义，写作 Agent 的编辑器和版本管理是 Harness，客服 Agent 接的知识库和工单系统是，你给个人 Agent 写的那份很长的偏好说明也是。更早的 Prompt Engineering 和 Context Engineering 同样属于这个范畴，只是当时还没有人用这个词，做的事也主要是其中一种：**教模型把某一步做对。**

它也有边界：必须落到 Agent 参与的工作上。公司的请假制度、团队的周会本身不是 Harness，那是人和人之间的管理；但当你让 Agent 替你提交请假，它需要知道走哪个流程、谁来审批、批完通知谁——把这些接给它的那一部分才是。

这套机制有多重要？两个例子，共同点是模型没换，只改了外面：

- 开头那件事：早期 Codex 改完文件不会跑测试，Tibo 团队在提示词里加了一句提醒，它就开始跑了；
- 反方向的例子：Opus 5 发布时，Claude Code 的作者 Boris Cherny 把系统提示词删掉了 80%——很多内容是在纠正旧模型的问题，新模型已经没有这些问题了，去掉之后表现反而略有提升。

**这套机制做对了，模型的能力才发挥得出来；过时了，反过来会拖累模型。** 很多看起来是"模型不行"的问题，根源其实在 Harness。

## 二、补上去的东西，模型迟早自己会

这个现象在过去几年反复出现：

| 补丁 | 补的是什么 | 后来 |
|---|---|---|
| "Let's think step by step" | 2022 年发现提示词末尾加这句，推理题正确率明显提高 | 2024 年推理模型出现，"先思考再回答"被训练进模型，没人再写 |
| 解析文本的工具调用 | 提示词里约定输出格式，外部程序解析执行 | function calling 成为模型原生能力，解析那层代码不再需要（但工具仍在模型外执行） |
| Todo List 工具 | Sonnet 3.5 时代交给模型五件事，它往往做完三件就停，加个待办列表效果明显 | Claude Code v2.1.233（2026-08-14）起，TodoWrite 等五个待办工具在 Opus 4.8、Sonnet 5 等新模型上默认不再提供 |

为什么总是先在外面做、之后才进到模型里？**因为在外面试错的成本低**：改一句提示词只要几分钟，效果当场能看到；训练模型以月为单位，而且得先知道要训练什么——"要训练什么"的答案，恰恰是在模型外面、在真实用户的使用中一点点试出来的。Tibo 说这些补丁像拐杖，Joye 觉得不太准确：拐杖是伤好就扔的东西，而这些补丁更像是**替下一代模型探路**——今天在外面验证过的做法，就是明天模型应该具备的能力。探路的不只是模型厂商，step by step 和早期工具调用最初都来自论文和开发者社区。

### 退场的原因不止一种

回头数删掉过的东西，旧实现退场其实有三种原因，混在一起说很容易得出"Harness 迟早都会进模型"的结论：

- **模型已学会。** 主动跑测试、先思考再回答、做完五件事再停——真的被模型学走了，外面那句提醒可以直接删；
- **平台已承接。** 前两年做 Agent 记忆要自己搭、接每个外部系统都要写连接代码；现在记忆是各家产品内置功能，MCP 是公共协议，集成平台替你做好——自己写的可以删了，但这件事并没有进模型，只是换了承接的人；
- **协作方式改变。** AskUserQuestion 这个工具作者花了很长时间设计，后来自己也很少用了——直接让 Claude 生成一个可交互的 HTML 页面来提问。固定的提问工具退场了，"Agent 需要向人把事情问清楚"一点没变，变的只是形式。

**三种原因都会让旧实现退场，但只有第一种可以说是被模型吸收**；后两种情况下，需求原封不动还在，只是实现换了地方或形式。

### 哪些东西模型学不走

判断方法很简单，只问一个问题：**假如模型已经足够聪明，这段代码还有没有存在的必要？**

提醒跑测试、提醒不要半途而废，都是在教模型完成某一步，迟早被学走。但下面这些是人和 Agent 一起做事本身就需要的，模型再聪明也得有人在外面做：

| 学不走的东西 | 为什么 |
|---|---|
| 取回真实的结果 | "测试通过了"从模型口中说出来只是一句话，真实退出码要程序取。模型越强，完成报告读起来越可靠，越难靠读报告发现问题——CI 红绿必须程序确认 |
| 权限和边界 | "它会选择不读这个目录"和"它读不了这个目录"是两回事，只有后者才是保证。规则可以模型起草，执行必须交给沙箱和权限系统 |
| 进度和触发 | 模型只在被调用的那几秒存在。定时任务谁触发、崩溃后从哪继续、哪些操作不能重复，都发生在模型不在场的时候 |
| 通往真实世界的接口 | 模型再聪明也接触不到没接给它的东西：数据库、内部系统、IM、邮箱、支付 |
| 人在哪里介入 | 怎么看到它正在做什么、哪一步可打断、哪些操作要人确认 |
| 成本 | 用哪个模型、同时开几路、预算花到多少停——付账的是你 |
| 追查和撤回 | 它替你做的事越多，事后能不能说清"当时做了什么、为什么这么做"、做错了能不能撤回，越重要 |

而且**模型越强，这些部分的分量越重**——越敢让它在无人值守下运行更长时间，需要核对的结果、管理的权限、衔接的断点都随之增加。Boris 的印证：Claude Code 每发布一个新模型就删一轮 harness 代码，今天剩下的几乎全是**安全、权限和静态分析，加上大量 UI 代码**——安全权限对应边界，静态分析对应真实结果，UI 对应人的介入。

最后还有一样学不走的东西：**只属于你、你的组织或企业的上下文**——团队为什么这样决定、企业内部流程为什么是现在这样、你的用户说"老样子"指什么、什么样的结果在你的场景里才算合格。

### 拿 Skills 来验证一下

这个问题也可以看最近很热的 Skills。Superpowers 是过去一年最流行的开发流程 Skills：先 brainstorm、拆任务、强制 TDD、做完 review——相当于给 coding agent 装了一整套软件开发方法论。GPT-6 发布后很多人转向 Matt Pocock 的 grill-me：轻得多，核心只有一件事——动手前反过来追问你，直到方案里每个没想清楚的地方都问明白。

这变化和前面是同一件事：Superpowers 补的是模型在"怎么规划、怎么执行"上的判断，模型自己具备了，这套流程就从帮助变成负担；grill-me 留下的部分是把只有你知道的信息从你这里问出来——但下一代 SOTA 模型很可能自己就知道什么时候该停下提问，到那时 grill-me 同样会被淘汰。

Skills 这种形式本身不会淘汰，但最后剩下的价值很可能只有一点：**方便传播**。一份垂类 know-how 打包成 Skill，别人装上就能用——只不过拿到垂类 Skill 后，还是应该拆开融进自己的 Agent 和 workflow。

## 三、教模型的部分在变小，协作的部分在变大

Tibo 说的 Harness 是 Codex 团队维护的核心 runtime（沙箱、工具、每轮开头的说明），在那个范围里他说得对——这部分确实在变小，而且应该变小。

但同一期节目里，Tibo 还讲了另外几件事：OpenAI 内部的 Codex 默认接入了 Slack、全部文档和全部代码，新人遇到问题先被问"你问过 Codex 了吗"；使用场景从写代码扩展到 finance、marketing。**这些事情没有一件是在教模型完成某一步，全都是在让更多的人、更多的工作能和 Agent 接上。**

所以 Joye 的判断：

> **模型变强，减少的是教它完成某一步的机制；更多的人把更多的工作交给 Agent，增加的是让彼此协作的机制。**

Claude Code 团队说得更直接：讲完 Todo List 退场后，另一位成员补充——这些功能当初是弥补模型缺陷，模型变好就可以拿掉；但与此同时，他们交给 Claude Code 的任务变得更大更难，要在更大的任务上保持连贯，模型又需要新的工具。**删掉一批补丁 → 能交给 Agent 的任务变大 → 新的协作问题又冒出来。** 这和他之前写的 Prompt → Context → Harness → Loop 演进线是同一个规律：前一个问题稳定了，着手的地方就移到下一个，而原来那部分并没有消失，只是成了新问题的基础。

协作的问题现在长到了哪里？按"谁和谁在协作"，Joye 把它分成三种尺度：

| 尺度 | 谁和谁在协作 | 要解决什么 | 会退场的 | 长期要做的 |
|---|---|---|---|---|
| **产品级** | 一个用户 × 一个 Agent | 表达需求、补信息、调结果、确认执行 | 提醒类补丁被模型学走；记忆和通用集成被平台做成标配；固定提问工具被可交互 HTML 取代 | 你的工具、确认和撤回的方式，以及垂类里才有的做法（设计、剪辑、市场研究才刚开始探索） |
| **Repo 级** | 一个开发团队 × 各自的 coding agent | 共享约定、感知彼此的工作、交接、验证合并 | 读仓库、跑 review 这类通用做法被 coding agent 内置 | 开发规范、历史遗留问题的来龙去脉、谁的 Agent 正在改什么、issue 之间的依赖冲突——以前靠问同事，现在要变成 Agent 读得到的形式 |
| **组织级** | 不同角色的团队 × 他们的 Agent | 获取业务背景、跨角色推进、授权、反馈闭环 | 运行在 IM 里的 Agent 这种形态会成为平台出售的产品 | 授权和反馈的通道，以及"当初为什么这样决定"的历史——只属于你或你的组织，不在任何人的训练数据里 |

设想一个 5 人开发团队每人配一个 coding agent：每个 Agent 单独看都没问题，放在一起就出现新问题——A 的 Agent 改了接口约定，B 的 Agent 不知道又按旧约定写调用；两个 issue 单独看都合理、改的却是同一块逻辑还互相矛盾；历史遗留问题没人写下来；每个 Agent 进仓库都要重新熟悉一遍；规范只存在人脑子里。没有 AI 时这些靠**问同事**——这些知识一直在，只是存在人的脑子里和聊天记录里，从来不在仓库里。所以要尽可能让仓库变得 **agent friendly**：最基本的四样是 AGENTS.md（Claude Code 里是 CLAUDE.md）、CI/CD、文档、repo index（给 Agent 看的仓库地图）。

Joye 自己的博客仓库就是个例子：CLAUDE.md 里有一条"**不要直接 push 到 main，先推到分支，等我看过预览再合并**"——出过一次问题才加的：有一次 Agent 写完文章直接推到 main，而 main 是自动部署的，文章在他看过之前就上线了。Agent 并没有做错什么，只是没人告诉它。

Bun 从 Zig 重写为 Rust 也说明这个尺度的分量：Bun 团队的 Jarred 每逢新一代模型发布就把这个任务交给它试一次，直到有一代模型做成了——按 Boris 的说法，那是一个 prompt 加上调度大量 Agent 的工作流，一共运行了 11 天。这件事能成，关键不在提示词，而在于 Bun 和 Node.js 本来就有一大套现成的测试。**"能不能验证"比"指令怎么写"更重要，而能不能验证取决于仓库本身。**

三种尺度不是一层包着一层、也不需要按顺序走——一个人做个人项目也可以在 Telegram 里让 Agent 跨几件事推进；同一件事也常同时落在几种尺度上。比例规律：**协作的范围越大，属于自己的部分占比越高，也就越难被学走。** 组织级的主体是一个组织自己的决策历史，它不在任何人的训练数据里。

## 四、做 Agent 产品要算一笔账：Harness 要涨得比模型快

用户为什么用你的产品，而不是直接打开 ChatGPT 或 Claude？因为同一件事交给你的产品更省心、结果更好，拆开看大致是：中途人工介入次数更少；前期不用花时间沟通需求（它已了解你的场景和偏好）；最后结果更好、返工更少；有些事情裸模型根本做不了（接不到你的数据和系统）。

这些加在一起，就是产品相对裸模型多出来的部分。问题在于：**模型每隔几个月就变强一次，这一部分会被它一点点追平。** 所以只是"现在比裸模型强"还不够——**你的 Harness 必须增长得比模型快**。增长的速度就是斜率：Harness 的斜率要高于底层模型的斜率，否则每过一代模型，领先的部分就变薄一些。Todo List 就是例子：在 Sonnet 3.5 阶段它是实实在在的领先，但这是一次性领先，一年后模型自己追平了。**当前领先多少并不说明问题，能不能持续领先才是关键。**

斜率由什么决定？三点：

1. **试错的成本。** coding agent 的 Harness 发展这么快，很大程度上因为代码非常适合试错：输出是文本，可以 diff、可以运行、有退出码，试一次几乎没有成本；
2. **有没有别人拿不到的输入。** 私有数据、真实用户反馈、某个行业具体的工作方式——通用的技巧人人都会，也都会被模型学走；
3. **多做出来的部分有没有人买单。** 也就是有没有增量市场。如果需求是固定蛋糕，模型每进步一点就替代你一点，你增长得再快也只是在防守——做 Agent 产品一定要找有增量市场的方向。

### 为什么不太看好 AI 视频的衍生应用

用这三点看这半年最热的基于 AI 视频/生图的衍生应用（做设计、批量短剧、营销视频），其中 To C 那一大批并不被看好：

- **试错成本高。** 以字节 Seedance 2.5 为例：火山方舟按 token 计费，不含参考视频时每百万 token 70 元，折算 480p 每秒约 0.67 元、720p 每秒约 1.51 元；一条 30 秒 720p 的片子生成一次就是约 45 元。coding agent 里"生成、检查、不合格就重来、开十路选最好的"放到视频上——10 路、重来 3 轮，就是一千三百多元，最后用上的只有一条；
- **质量难验证。** 代码改坏了测试会告诉你；视频输出是像素，没有 diff 也没有退出码。同一段提示词生成两次得到两条不同的片子；想改一个镜头里的细节往往要整段重生成，重生成又带来新问题（脸变了、光线对不上、接不起来）。"这个镜头好不好"只能人一条条看——上一节说"能不能验证比指令怎么写更重要"，视频缺的恰恰是这一环，自动检查、不合格重来的循环转不起来；
- **Harness 普遍很薄。** 提示词模板、分镜拆解、素材拼接、好看的界面——成片质量每一次明显提升（人物一致性、时长、口型）都来自底层模型换代，而不是产品自身，而模型进步的好处所有调用同一 API 的竞品会同时得到。产品里投入最多的工程（为保持人物一致性做的变通、为延长时长做的分段拼接）恰恰是下一代模型最先解决的问题；
- **To C 没人买单。** AI 降低了制作成本，但成本是给所有人同时降低的——内容供给一下多了很多，观众的时间和付费意愿却没跟着变多，利润不会留在制作环节。

结论：**这半年视频生成的热潮里，最大的赢家是模型厂商**——下游产品无论怎么打折、换算成积分和会员，本质上都是在卖 token，并没有在模型之上做出一层足够好的视频 Harness。

### 生图为什么好一些，MiniMax-H3 为什么不一样

生图的情况要好一些：图像 API 便宜得多、能力成熟更早，可操作空间大（一次生成几张挑选、局部重绘、条件控制构图、节点式工作流），试得起，也确实形成了不小的工具生态。

MiniMax-H3 和 Seedance 一样是视频生成模型，但走了另一条路：**公开权重**（Hugging Face 发布），可以量化、在低算力机器上本地部署——按 ComfyUI 官方的说法，量化后在 RTX 3060 这样的消费级显卡上就能跑。它的意义在于把"试一次"的成本从按次付费变成一次性硬件投入加电费：多路生成再挑选、不合格就重来、围绕自己素材搭流水线，这些按量计费时算不过账的做法现在算得过来了——**平民玩家第一次有条件在视频上认真做 Harness**。

需要提醒两点：开放权重版原生是 768p、单段最长 15 秒，用的是 MiniMax 自己的社区许可，对地区和商用有限制，不是无条件开源；成本是给所有人同时降低的，它只解决了"试不试得起"——质量怎么验证、有没有别人拿不到的输入、有没有人买单，仍然要自己回答。

### 哪些情况仍然值得做

- **To B，或者手里有私有数据和流程。** 品牌的素材库和视觉规范、电商的商品库、行业的合规规则——这些是别人拿不到的，而且模型越强它们价值越大；
- **本来就有 IP 或流量。** 这种情况下 AI 只是降低成本的工具，护城河本来就不在 Harness 上；
- **把精力放在可以修改、可以检查的中间产物上，而不是像素上。** 剧本、分镜、时间线、图层——这些是文本和结构，可以 diff、可以检查、可以局部修改。

斜率没法精确测量，但可以粗略估计：准备一组自己场景里的真实任务，每次底层模型换代时跑两遍——一遍用完整产品，一遍用裸模型加最薄一层封装——把两者的差距连续记录两三代，是在变大还是变小就很清楚了。

## 五、Joye 自己的做法

模型厂商可以选择"这个先不做，等下一代模型"，因为他们看得到训练计划；Joye 看不到——他用的是别人的模型，不知道哪个问题正在被修复，而他的用户今天就有事情要完成。所以**补丁还是要打，只是打法要变**，他给自己定了三条：

**第一，通用的补丁按短期来做。** 一块通用 Harness 能保持价值的时间大概只有一两代模型，也就是一年左右——不代表不值得做（提前一代用上某种能力，在这个行业里就是实实在在的时间窗口），只是不再为它投入需要两三年才能回本的工程量。如果发现自己为了绕开模型的某个缺陷已经写了成千上万行代码，先停下来想想是不是方向错了。

**第二，加补丁的时候，同时留下一个可以重跑的失败案例。** 案例要具体："模型不够主动"没有用，"改完三个文件之后没有跑 check 就报告完成"才有用。新模型发布后，带补丁和不带补丁各跑几遍，不带补丁也能通过，就删掉。写给 Agent 的说明文件和 Skills 也一样，隔段时间清理一遍，而不是只加不减。删不掉的补丁同样有信息量——"请先向用户确认再执行"这类补丁其实说明权限检查没在程序里实现、只能写给模型看，它不应该删，而应该从提示词移到代码里。这组案例还有一个用途：平台本身也在变（Claude Code 一次普通版本升级，Agent 可用工具就少了五个），底层更新后在自己任务上是变好还是变差，也只能靠这组案例回答。

**第三，把长期的投入放在协作机制和只属于自己的上下文上。** 权限、状态、交接、反馈是人和 Agent 一起做事的长期需求，实现可以换、需求不会退场；上下文是个人的、组织的、企业的。会被学走的是几百万用户共有的行为（跑测试、不跑偏、正确使用工具）——正面去做一个通用 Agent，没有数据也没有入口，模型一更新价值就缩水，这条路一直不看好。

> **智能可以租，上下文只能自己积累。**

这也是为什么垂类做得越深，越应该主动接入通用 Agent：把你的 know-how 做成 MCP、插件或者 Skill，接到别人已经在使用的 Agent 上，底层怎么更替都不受影响。

## 写在最后

说回 Gergely 那句"有点泄气"的话。它的背后有一个没说出来的前提：**一份工作的价值，取决于它产出的代码能存活多久**——按这个标准，这一行确实让人泄气，因为模型外面的代码注定存活不了多久。

Joye 不这样衡量：在模型外面做的东西被模型学走了，说明这件事做对了，说明比模型早一代看到了这种能力应该是什么样子。代码会被删掉，但"早一代看到"的经验会留在身上，它还决定能不能看到下一个问题在哪里——亲手做过前一个问题的人，最先知道它什么时候稳定了，也最先遇到协作范围变大之后的新问题。

播客最后，Thariq 问同事是否怀念过去手写代码的方式：一位说以前喜欢打磨 UI 细节，曾花一整天叠加径向渐变只为复刻 Mac OS 10.4 的 Aqua 按钮，现在不会手工做这些了——但这让他想起七八岁时想做游戏却不会写代码、只能用 PowerPoint 拼出可点击的形状；而现在，整个软件工程都触手可及，不必再因为不掌握某项技术就放弃一个想法。**失去的是在某一件事上打磨到极致的手艺，得到的是去做更大的事的能力。**

如果你的整个产品只是一块通用补丁，除此之外什么都没有，那么泄气是合理的——它是一个很准确的信号：你的斜率已经落后于模型，该换到更大的协作尺度上去，或者往垂类里再深入一层。

我自己记下的几条：

- **这篇与系列前两篇是同一个框架的三个切面**：《读我办了一场Agent比赛》里"能用 Hook 解决的先别做 Harness"是"教的部分会被学走"的雏形；《Personal Agent 拆解》里的"补偿层 vs 承载层"就是这篇"教 vs 协作"的另一种表达——补偿层对应教模型做某一步（会退场），承载层对应权限、状态、交接、反馈（要加厚）；
- 可直接复用的检验问题：**假如模型已经足够聪明，这一块还有没有存在的必要？** 如果没有，它退场的时候，背后的需求会由谁来接？
- 三种协作尺度给自己定位：个人项目目前多半落在产品级和 Repo 级之间；把"以前问同事才知道的事"变成 Agent 读得到的形式（CLAUDE.md、文档、repo index），是最容易立刻开始的 Repo 级动作；
- "智能可以租，上下文只能自己积累"——做 Agent 产品，护城河是自有数据、业务理解和增量市场，不是通用补丁。
