# Agent 求职避坑：读一场 80 分钟模拟面试复盘

## 前言

这是 [Joye](https://www.joyehuang.me) 写的一篇模拟面试复盘：他和另一位面试官 W 面了一位想转 Agent 开发的同学 80 分钟，候选人简历上挂着两个看起来很豪华的项目——LangGraph 多 Agent 健康饮食助手、Agent 长期记忆引擎，GraphRAG、图向量混合检索、微调一应俱全。

结果一句话就让项目站不住了：

> “如果是我，我用豆包就能解决，为什么一定要做这个？”

原文把每道题、候选人的回答、面试官的评价、以及“换我会怎么答”全部摊开，是 2026 年 Agent 岗求职的一手地图。这篇笔记把核心内容整理如下。

---

## 一、灵魂一问：你解决了什么真实问题

面试官想看到的故事线是：**识别了一个真实问题 → 选了合适的技术 → 解决得比现成方案好**。

> 项目存在的合理性 = 真实问题 × 现成方案的不足。

候选人的路径恰好相反：先决定要用 LangGraph / 多 Agent / GraphRAG / 微调，再找个场景把这些技术塞进去。“AI 饮食推荐”这种场景，豆包、ChatGPT、Kimi 直接对话就能解决，所有架构复杂度都没有对应的回报。

写项目之前先问自己三个问题：

1. 这个场景用 ChatGPT / 豆包 / Claude 直接对话能不能解决？能，就换场景。
2. 我的多 Agent 相比单 Agent 有什么实质收益？说不出来，就改成单 Agent。
3. 每一个技术选型能不能讲清楚“为什么是它，不是别的”？讲不清的，删掉或补功课。

找项目的两个方向：从自己身边的真实需求出发（故事线立得住）；或深度体验一个开源 Agent，找到不足做二次开发（难，但含金量极高）。**现在有了 AI，从 0 搓一个项目的成本已经很低了，没必要抄。**

---

## 二、“为什么用 X 不用 Y”：一问就漏的选型题

整场面试问得最多的就是选型题，因为它一句话就能区分“真正用过、踩过坑”和“看博客抄简历”。

| 问题 | 候选人的回答 | 面试官想要的 |
|------|------------|------------|
| 为什么用 Milvus / ChromaDB？ | “一个数据量大，一个小” | 部署形态、生态、pgvector/Qdrant 等替代品；更高分是直接挑战选型：“这个数据量 pgvector 完全够了” |
| 多 Agent 用不同模型吗？ | “全用 Qwen 一个模型” | 按职责分级：意图识别用小模型、推理用大模型、异步摘要用便宜模型——这是生产视角 |
| Agent 之间有交流吗？ | “没什么交流，就是编排好的 workflow” | 那就不叫 Multi-Agent。固定路由分发 + 汇总 = Workflow；多 Agent 需要自主决策、互相调用通信 |
| 单 Agent 和多 Agent 编排各自的优劣？ | 只答了“prompt 隔离、focus 在自己任务” | 多 Agent：上下文隔离、可单独换模型、能并行、可观测性需要主动设计（有 replay 更加分）；代价是延迟高、token 成倍增长、路由本身可能错。单 Agent：简单便宜、全局视野、有 Skills 加持已成新范式；代价是上下文易爆 |
| 意图识别 90.6% 怎么算的？ | “造了 200 个问题对答案” | 测试集怎么构建、覆盖哪些 case、指标是什么、怎么自动化回归、识别不了怎么兜底 |
| 为什么用 Redis？ | “TTL 做记忆过期” | 大错：**记忆过期不该是删掉而是 archive**。Redis 真正用途是缓存、分布式锁、会话隔离、限流、临时 checkpoint |
| PostgreSQL vs MySQL？ | “PG 企业级，能加 pgvector” | 2026 年起新项目基本用 PG：pgvector 干掉独立向量库、jsonb、地理空间；MySQL 的认知滞后了 |
| 为什么用 Neo4j 不用 Redis 存图？为什么不用 Neo4j 存 Agent 状态？ | 讲 Redis 用途时顺手把“图存储”说成 Redis 的功能，当场被揪出来 | 这是 W 的钓鱼题。真正要学的是：不要在自己不熟的领域做发散性回答 |
| 为什么 Qwen3-8B 微调、Kimi K2.5 生成数据？ | “Kimi 构建问答对” | 数据蒸馏逻辑合理，但要讲清楚数据质量 × 任务匹配度 × 成本 |

两条铁律：**被问到不熟的就承认，不要嘴硬被钓鱼**；**简历上写的每一点都要能理解透，写了我就会问**。还有一条来自那道 Neo4j 钓鱼题：**不要在不熟的领域发散性回答**——被问 Redis 就老实讲 Redis 的合理用途，别为了显得懂得多，把图存储、向量、状态机管理都扯进来。

另外 Joye 和 W 还顺嘴吐槽了一句：Qwen3-8B 在培训班项目里太常见，“看到就有 PTSD”。想让面试官眼前一亮，至少用一个 2026 年的最新模型版本。

## 三、Memory 与上下文工程：细节里全是坑

**记忆写入的灵魂问题**：用户说“今天想吃辣”，该记还是不该记？

- **事实型**（我叫 XX）→ 直接写入，高置信度；**推导型**（经常周末加班）→ 不写，可从历史推导；**偏好型**（我喜欢吃辣）→ 写入但标注置信度和时效性
- **短期偏好**（今天想吃辣）→ 会话级记忆，结束就衰减；**长期偏好**（多次出现、稳定）→ 升级为长期记忆，依据“出现次数 + 时间跨度”
- **矛盾检测**：“我喜欢吃辣”vs“我不能吃辣”——时间戳 + 上下文判断当前事实
- **写入触发**：显式（“请记住我…”）、隐式（会话结束 / 达到阈值）、异步（后台便宜模型总结提取）

**Memory 加在 system prompt 的哪个位置？** 候选人答“靠后，模型对靠后内容更敏感”——**完全说反了，要加在最前面，核心是 prefix caching**：

> 把变化最少的内容放最前面：system prompt → 长期记忆 → 工具描述 → 历史会话 → 当前 query。这样大部分时候只有最后一段在变，前缀全部命中缓存。如果把 memory 放最后，每次记忆更新都会破坏整个前缀缓存，token 成本飙升。

**Skills / MCP / Function Calling 的关系**——一张表说清：

| 层 | 解决什么问题 | 形式 |
|----|------------|------|
| Function Calling | 给模型加可执行能力 | 单个函数定义 |
| MCP | 标准化“模型 ↔ 工具/数据源”连接 | 一个 server 暴露一组 tool/resource |
| Skills | 给模型“如何完成一类任务”的程序化指南 | 文件夹（SKILL.md + 资源） |

MCP 给数据，Skill 给方法论。Skill 的核心设计是**渐进式披露**：第一层只加载元数据（name + description），命中后才加载完整内容——几十个 skill 每个几千字，全塞 prompt 就爆了。Claude Code 的 tool_search 更进一步，把工具列表本身也变成可搜索索引、按需加载。

## 四、Agent 成本控制五板斧

“减少调用次数”这种回答等于“我每个月想少花钱”——是结果不是方法。真正的方法：

1. **Prefix caching 友好的上下文设计**（如上）
2. **模型分级**：简单任务小模型，复杂推理大模型
3. **减少 step 数**：Agent 的 token 成本是指数级的——每多一步，整个历史就作为输入再发一次。工具设计要“宽口径”，Plan 阶段尽量完整
4. **上下文剪枝**：用过的工具结果删掉保留摘要、文件只留 diff、大段内容按需读取
5. **失败重试限流**：不限制重试次数 + 不做指数退避，一个 bug 就能让账单爆炸

## 五、Claude Code 没有 RAG，它用的是 grep

全文最深刻的一个观察。W 问：“RAG 是为了解决知识库问题，那最新的 Agent 怎么解决的？Claude Code 有 RAG 吗？”

**没有。它用的是 grep。**

- 传统 RAG 是 2023 年的方法论：文档切片向量化、查询时检索，假设“上下文小、token 贵”
- 2025–2026 年的范式是**长上下文模型 + 工具**：让 Agent 用 grep / glob / read 自己探索，精度更高、不依赖向量化质量、不需要维护索引
- RAG 没死，但**不再是唯一答案**——“简历上用了 RAG”已经不加分，写了就要能说清“为什么 RAG 比 Agent + grep 更适合这个场景”

配套的趋势判断：**业界正从“花式多 Agent 编排”往“单个强 Agent + 好的工具 + 好的上下文工程”回归**，Claude Code、Cursor Agent、Cline 都是这一范式。

## 六、软实力：信息源、海外生态与表达

- **一手信息源决定天花板**。只看公众号 / 知乎 / CSDN，看到的永远是二手、滞后的信息。要建立 X（关注 Anthropic / OpenAI 员工和独立开发者）、Hacker News、官方 changelog、GitHub 新项目这样的信息源。“刷多了解多了，就是降维打击——你就从求职者变成正在参与这场构建的人。”
- **海外开发者生态是被国内候选人忽视的加分项**：Google OAuth、Stripe 支付、Vercel 部署、one-click deploy……“开发圈应该只分中国和海外。”
- **表达能力被严重低估**：先结论后细节（30 秒切入核心）、用专业术语（“知识到位但词没到位”照样被判不熟）、录音回放改填充词。绕弯子的本质往往是心里没底想蒙混——**承认不会，比硬撑被钓鱼问到死好得多**。
- **AI Coding 考的是过程**：大家都用 AI 写代码、简历长得都差不多，真正区分候选人的是你怎么用——AGENTS.md / CLAUDE.md / 项目 doc tree、常用框架最佳实践沉淀成 skill、可观测性与 evaluation 怎么做。
- **项目要上线**：部署到 Vercel 半小时就好，“能摸到的项目”比纯简历描述可信太多。

## 七、自检清单

把整场面试的教训浓缩成五层 checklist：

- **项目层**：解决的是直接对话**不能**解决的问题吗？多 Agent 有实质收益吗？上线了吗？能体验吗？
- **选型层**：每个技术都能答“为什么是它，不是 X/Y/Z”吗？知道 pgvector 能替代独立向量库吗？知道 Claude Code 用 grep 不用 RAG 吗？模型分级了吗？
- **知识层**：Function Calling / MCP / Skills 的关系？渐进式披露？prefix caching 友好设计？记忆分类与矛盾处理？OpenAI / Claude / 开源 Agent 的 Memory 演进？
- **工作流层**：有自己的 AI Coding 工作流吗？除了写代码还怎么用 AI？会写 evaluation 吗？
- **软能力层**：一手信息源是什么？了解海外生态吗？回答能 30 秒切入核心吗？

## 写在最后

读这篇的时候我一直在想 [编程面试大学](/2026/09/12/编程面试大学/) 那篇文章——一个讲的是“知识面怎么铺”，这篇讲的是“项目和表达怎么立”，恰好互补。而对于还在用培训班项目攒简历的同学（包括我），最该记住的是第一部分那三个问题：**技术是答案，但你得先有真问题**。
