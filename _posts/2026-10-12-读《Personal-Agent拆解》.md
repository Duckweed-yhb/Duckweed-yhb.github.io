# 模型越强，产品越要做减法：读 Joye 的 Personal Agent 拆解

## 前言

本文整理自 Joye 在 2026-10-11 发布的[《Personal Agent 拆解：模型越强，产品越要做减法》](https://www.joyehuang.me/blog/20261011---alwaysonagents/post)。

这篇的起点是 Lee Robinson 在 Stanford CS146S 的一堂课（主题：常驻、主动的 Agent 是怎么工作的）。Lee 之前在 Vercel 负责开发者体验，后来去 Cursor 做 Agent 产品，现在在 SpaceX 做 **Grok Bot**。讲座快结束时他提了一条前后只讲了不到一分钟的原则：**delete the product，删掉产品**——而回头看，前面讲的几乎每一个架构设计都能用它来解释。

Joye 自己的主力 Agent 跑在家里的 Mac mini 上，随时能在 Telegram 里找到它，"已经不太像一个工具，更像一个同事"。这篇承接他上一篇（我办了一场 Agent 比赛），把「删」这个动作本身拆开来讲。

以下按原文脉络条理化整理，观点与细节归原作者。

---

## 一、从「发一条等一条」到同事

Lee 把 Agent 产品的演进分成四个阶段：

| 阶段 | 形态 | 瓶颈 |
|---|---|---|
| 1 | 复制粘贴：从 ChatGPT 复制代码粘回编辑器 | 人手动搬运 |
| 2 | 终端里的 Harness：模型自己改文件、跑命令 | 单机串行 |
| 3 | 专门的 App：云端同时跑很多 Agent | 人成了瓶颈——每条命令都要等你审批 |
| 4 | **常驻 Agent** | 异步、自主、不需要你盯 |

Joye 自己按三种形态划分 Agent 产品：网页端 Agent（回答问题的机器）；装在电脑上的 coding agent（Claude Code、Cursor、Codex）；以及跑在云端、在聊天软件里就能找到的 bot——**personal agent**。Grok Bot 属于第三种。

第三种真正改变了使用方式：最早是"我发一条，等它做完，才能发下一条"；现在更像和同事共事——可以随时插话，先说"去看一下这个帖子"，再补一句"其实周四再做也行"，它能理解这两句话说的是同一件事。Lee 的原话：**"It knows when to be quiet."**

和 coding agent 相比，personal agent 的差别主要在这四点：

- **它一直在线。** 你合上电脑、它自己重启、中途崩溃，都不影响它继续干活；
- **它有自己的电脑。** 一台云端的机器，有桌面、文件和浏览器；
- **唤醒它的不只是你。** Slack 里有人 @ 你、收到邮件、定时任务到点，都可以把它叫起来；
- **它要连续工作很久。** 不是几个小时，而是几天、几周、甚至几个月。

这类产品大多做成 bot 形态——大家都发短信。Lee 顺口说了句后面会反复用到的话：**模型越强，界面反而越简单。**

Joye 的强烈建议是：花一周也好、几天也好，去真正用一用这类产品，这是最能改变想法的一件事。可用的有 Today（分国内/国外版）、Cue（Manus）、Muse（Meta，门槛高）、Dots（OpenAI，仅 Pro）、Grok Bot。

---

## 二、Grok Bot 是怎么搭起来的

Grok Bot 的内核依然是最小的 Agent——模型在循环里调用工具，变化都在外面那一圈。Lee 把架构分成三段：**左边触发器 → 中间厚服务器 → 右边 Agent 自己的电脑。**

**① 触发器**：你直接发消息、Slack/群聊里 @ 它、邮件、电话/会议、定时任务……消息从不同来源进来。

**② 服务器（厚）**：消息先进一个路由器——去重、按来源定优先级、连续几条合并成一轮处理，再判断**要不要打扰用户**。这一点和真实的同事很像：一个同事每有一点进展就来找你汇报，你会觉得很烦，大多数任务一天更新一次状态就够了。优先级里最重要的一条是：**你直接发给它的消息高于一切**——你一开口，它就先放下手上的事。

服务器里还有 Agent loop（模型在循环里调用工具，每个任务是持久化工作流，崩溃后从断点继续）和数据库（对话日志、记忆、定时任务、状态，每一轮都写进来）。

**③ Agent 的电脑**：一台按需启动的云上虚拟机（Firecracker），用的时候启动、用完做快照然后休眠——一直开着太贵。有一个很值得一提的设计：**Agent loop 不放在这台电脑里，而是放在服务器上**，所以电脑可以随时重建（比如紧急安全漏洞，直接重建所有虚拟机打补丁），Agent 不会停下来。你可以随时连进去看它在做什么，必要时亲手接管。

---

## 三、客户端和服务器之间只有一个工具

Grok Bot 还有一个很能说明问题的设计：客户端（手机 App、桌面 App、邮件、Slack）和服务器之间只有**一个工具**，叫 `SendToUser`。

客户端只是在给服务器"发短信"：收到消息后按内容决定渲染形式——需要登录就弹登录表单，发邮件这类不可逆操作先给你一份草稿确认，不需要回话时回一个表情就够了。加一个新渠道不用改 Agent 的任何东西，只是多一个会收发消息的客户端。

工具都在服务器上，也尽量省着用：每次只把**工具名**发给模型，模型决定要用某个工具时才去读详细说明。遇到任务，它按一个**升级阶梯**来尝试——先试最便宜、最可靠的办法，不行再一级一级往上爬：

| 层级 | 手段 | 例子 |
|---|---|---|
| 1 | 已知上下文（对话历史） | "我们刚才约的是周几？" |
| 2 | 连接器 / MCP / API | 通过 Plaid 拉银行信息 |
| 3 | 网页搜索 | 昨晚小熊队的比分 |
| 4 | 浏览器 | 在一个没有 API 的网站上改预约 |
| 5 | 整个桌面（Linux 跑脚本/命令） | 给新功能录演示视频、构建东西 |
| 6 | 询问用户 | 输入、审批、2FA 验证码——以上都不行才打扰你 |

一个靠谱的同事也是这么做事的：先自己把能试的都试一遍，实在不行再来问你。

上下文同样省着用：Agent 每加一条消息基本是把整段对话重新发给模型，前面的部分和上一次完全一样就能命中缓存，价格便宜很多。所以 Lee 说，**出现缓存未命中，基本上就是系统里的一个 bug**——对一个一直在跑的常驻 Agent 来说，缓存命中率直接决定它养不养得起。

安全是同样的思路：每条命令执行前先让另一个模型审查一遍；收件箱里的邮件是不可信输入，不能当成你的指令。

## 四、为什么不直接交给 Codex 或 Claude Code

回到那个老问题：这些活，为什么不直接交给 Codex 或者 Claude Code？

Lee 讲了主 Agent 的设计：你和主 Agent 的对话很长、要求回复快，所以主 Agent 要保持**稀疏**——管理待办清单、查看进度、给帮手发消息；真正耗时间、耗 token 的工作交给子 Agent 带着全新上下文去做，最后只把结果带回来。

**如果你同时只有一个任务，直接交给 Codex 或 Claude Code 完全可以**——你的上下文和注意力都放在这一个任务上。

但当这个数字变成 5 个、10 个呢？这并不夸张：一个项目里的几个并行子任务，或几个项目同时推进。这时候瓶颈变成了你自己：每切换一次任务，都要重新回忆它做到哪一步、上下文是什么、下一步该说什么。**并行的任务越多，上下文和注意力的切换成本就越高**——所以才需要一个主 Agent（编排层）替你承担这部分。

Joye 自己的 Jojo 就是这么做的：任务交给它，它在 herdr 里为每个任务开独立工作区，拉起 Claude Code 或 Codex 干活，自己负责盯进度、做验收。默认情况下他只会听到两类消息："做完了"，以及需要他拍板的事。另一个好处是上手成本低：后台可以有很多 Agent，但你面对的只有一个。

不过这有一个前提：最强的那批模型要真的擅长多 Agent 协作。Joye 的观察是，这个能力在**今年下半年才有了一次很大的提升**——上半年 Claude 推出 agent teams、社区里也有类似产品，效果都不太好。

## 五、删掉产品

讲座后半段，Lee 讲了 Grok Bot 团队怎么让产品和模型一起变好：产品里的每一个错误都变成一条评测，先修 Harness；再定期用这些失败去训练新模型（后一步只有训练模型的团队能做）。然后他讲了那条原则——在 Cursor 和 SpaceX 都遵守的 **delete the product**：

> 你要真正接受一个假设：**今天的模型，是它们有史以来最差的**（"the models today are the worst they'll ever be"）。所以半年之后，你可能要把整个 UI 重做一遍。比较好的策略是为下一代模型而建：尽可能少建，只做一个非常简单的界面，让模型替你去思考和行动。

为什么"今天的模型最差"就意味着半年后要重做 UI？看 AI 写代码工具这几年的界面变化就清楚了：

| 阶段 | 界面 | 为什么需要它 |
|---|---|---|
| 1 | Tab 补全：补全这一行 | 补多了容易错 |
| 2 | 选中几行弹小对话框：只能改选中的行 | 放开了它可能会改乱 |
| 3 | 侧边栏 Ask/Plan/Agent 各种模式：先选模式 | 模型自己判断不好该先问、先规划还是直接动手 |
| 4 | 一个对话框：点进去直接说要做什么 | 模型足够强，不该用多余 UI 限制它 |

**UI 的复杂程度，往往是在弥补模型不够聪明的地方。** 表面看产品又回到了 ChatGPT 刚出来时的对话框——但这次回归不是因为模型只会聊天，而是因为模型已经足够强，我们不应该再用多余的 UI 去限制它。而且今天的对话框也不是空框：Opus 4.6 之后的模型能稳定输出复杂 JSON，产品准备一套组件，模型输出 JSON 就能直接渲染表单、卡片和图表——这就是**生成式 UI**。

回头看 Grok Bot 的每个设计——界面就是发短信、两端只有一个工具、工具只给名字、重活交给子 Agent、主 Agent 保持稀疏、没有模型选择器、不流式显示回复——几乎都是这条原则的结果。Lee 的总结："The best UI is none at all"，Grok Bot 能做成现在这样，"primarily because of everything we didn't have to build"。

最难的是把"今天的模型是最差的"真正内化：它意味着要随时准备推翻自己刚刚习惯的东西。**你现在为了弥补模型短板做的那部分 Harness，三个月、半年之后就是会被淘汰的。** 这不是谁做得不够好，而是这一行的底层逻辑：模型每隔几个月就换一代，今天替模型补上的东西迟早会被模型自己学会。认清这一点，才不会把一块注定要拆的脚手架当成护城河。Joye 的感慨：删掉产品，首先要删掉的，是自己已经习惯的那一套做法。

### 补偿层和承载层

不过"删掉产品"很容易被误读成"产品做得越少越好"。Joye 把一个 Agent 产品拆成两层：

- **补偿层**：因为模型还不够好，才替它做的那些事——替它做判断的流程和按钮、意图路由、一长串规则、手写的检索、为某一类任务专门做的小工具；
- **承载层**：不管模型多强都需要的东西——**数据、权限、集成、评测、分发和成本**。

打个比方：同样一件活，交给实习生要写清楚第一步第二步第三步，交给资深工程师只要告诉目标就够了。补偿层就是写给实习生的步骤说明——模型已经越来越像资深工程师，还给它详细步骤说明，反而是在限制它。

**「删掉产品」删的是补偿层**：要尽量薄、随时可以扔；**承载层不但不能删，还要持续加厚**。补偿层的价值随模型变强先升后降：模型弱的时候它让产品能用；到了交叉点该删；再往后变成负担——限制模型、和模型的判断冲突、占用上下文、还要人维护。

## 六、为什么补偿层留着反而有害

如果补偿层只是变得没用，留着也无所谓。问题在于它会**主动拖累更强的模型**，原因主要有四个：

**第一，它写死的是一个已经过期的假设。** 每一个专用工具、每一条预过滤、每一段手写检索，背后都有一个"模型做不到 X"的假设。Vercel 回顾他们的数据 Agent d0 时写道："We were doing the model's thinking for it."——原来有 17 个专用工具（查 schema、校验、错误恢复、规划），后来删到只剩两个（沙箱里的 bash + 执行 SQL）：

| 指标 | 旧架构（17 个工具） | bash + SQL（2 个工具） |
|---|---|---|
| 成功率 | 80% | **100%** |
| 平均耗时 | 274.8 秒 | **77.4 秒** |
| 平均 token | 约 102k | **约 61k** |
| 平均步数 | 约 12 步 | **约 7 步** |

（注：样本只有 5 条代表性查询，应看作很强的信号而非统计结论。前提是语义层本身是一份好文档——数据层一团乱的话，把文件系统交给模型只会更快得到错误查询。）

**第二，多余的约束会伤害强模型。** Anthropic 的 Thariq 介绍删掉 Claude Code 八成以上系统提示时列了几种典型伤害：互相打架的指令让模型先花力气调和；给的示例反而把模型限制在固定范围内；为防止最坏情况写的强规则换到另一类任务上就是错的。Every 的 Dan Shipper 在 Opus 5 发布当天也遇到同样的事：为旧模型攒的 skills 和新模型配合很差，全删了从头开始，表现明显变好。

**第三，每次换模型都要重新校准。** Vercel 的原话："every model update meant re-calibrating our constraints"——他们花在维护脚手架上的时间比改进 Agent 本身还多。补偿层的维护成本跟着模型的发布节奏走。

**第四，界面会把用户留在旧的用法里。** Amp 的 Thorsten Ball 说得很直接："If a feature teaches you to start using agents the old way, we need to remove it." Lee 发布 Cursor 3 时也承认，Cursor 2 频繁挪动 UI 让用户很烦，但 Agent 接手的工作越来越多，已经装不进 IDE 的界面了。

这四点之外还有一个人性上的原因（Hyung Won Chung 在 Stanford CS25 讲的）：结构是因为算力不够才加的，之后要删掉；但**大家擅长加结构，却不擅长删**。

所以"删掉产品"不是审美偏好，而是一笔期望值的计算：模型能力增长的速度，远远快过手写补丁能带来的提升。任何把人的判断硬编码进去的东西，都是在和这个速度对赌。往前可以追到 Rich Sutton 2019 年的 The Bitter Lesson：长期来看，能利用算力的通用方法最终胜出，人加进去的知识短期有帮助、长期会变成阻碍。

落到具体产品上，要问的其实是一个问题：**你的产品，能不能在模型变强的时候免费变好？** 最能直接检验的是 Manus 的 Peak Ji 给的指标：在同一个模型家族里，把弱模型换成强模型，你的架构能多拿到多少提升？差值越大，说明架构越能跟着模型一起变好；差值很小，说明补偿层在拖后腿。另外，换成不同家族的模型表现差距要尽量小——这说明你没有过度适配某一个模型。

## 七、哪些东西不能删，反而要加厚

如果只读到这里，很容易得出"什么都别做，等下一代模型"的结论——这是这条原则最容易被误用的地方。把补偿层、接口层、承载层画在一起：**每换一代模型，补偿层变薄，承载层变厚**；中间很薄的接口层（一个对话入口、少量基础工具、按需加载的 skills）基本不变；模型本身是外面的变量。

不能删的东西，都在最底下的承载层里：

- **数据与记忆**：用户画像、日志、可读的知识；
- **评测与 trace**：每个 bug 变成一条 eval；
- **集成与权限**：账号、支付、不可逆操作的审批；
- **分发与用户关系**：用户、社群、渠道；
- **运行时**：持久化、沙箱、缓存、成本上限。

逐个说几个关键的：

**评测。** 评测是唯一能告诉你"这块可以删了"的东西。Claude Code 敢删掉八成的系统提示，是因为有编码评测证明"没有可测量的损失"。没有评测，删就是在赌。Grok Bot 团队的做法也是这个道理：每个错误先变成一条评测，修完先在评测里验证。

**可靠性。** 模型会做，不等于每次都做对。Cognition 曾想让 Sonnet 4.5 自己写笔记替代自建的记忆系统，效果反而下降——模型不知道自己不知道什么。Lee 也提到：很多事都能用 shell 完成，但如果模型 90% 的时间都在用 shell 做同一件事，就值得做成专用工具——这类结构是为了稳定和可审查，不是为了补偿模型。

**权限和不可逆操作。** 发邮件前先确认草稿、每条命令先过审查、不可信输入不能当指令——这些是在划清责任边界，模型再强也要有。

**成本和缓存。** Manus 把 KV-cache 命中率看作生产环境里 Agent 最重要的单一指标，缓存和不缓存的价格能差十倍左右。缓存不会因为模型变强而过时，反而会随用量增加更重要。

**让人能快速核对的界面。** Karpathy 讲过，diff 视图的价值在于借用人的视觉系统缩短核对时间。Lee 说 Cursor 删到最后，编辑器还剩 2% 删不掉——那一部分就是留给人核对和微调的。

**可读的数据。** Vercel 的例子已经说明了：删工具之所以有效，是因为投入转移到了文档、命名和数据结构上。

有一个反对声音值得认真对待：Anthropic 可以为六个月之后的模型而建，是因为他们看得到模型路线图，大多数创业团队看不到。Joye 同意这一点，补了一句：模型厂商可以选择"这个先不做等下一代"，我们不行——**用户今天就有事情要完成**。所以补丁今天该打还是要打；"删掉产品"的意思不是事前不建，而是事后不留恋。

Joye 也给出了自己的折扣看法：Lee 的很多做法背后是有自己模型、有完整基础设施的大团队（预热缓存、持久化工作流、按需唤醒整台虚拟机），个人或小团队照搬扛不住；分层记忆和压缩策略对个人门槛太高，很多时候直接交给 Claude Code 自带的机制就够了；"The best UI is none at all"也说得太理想，不是所有产品都能只剩一个对话框。**先分清楚哪些是原则（谁都适用），哪些是规模带来的做法（要看自己的规模）。**

## 八、Joye 自己的做法

他运营的「副校长」bot 在一个约 800 人的 QQ 粉丝群里答疑。按"补偿层要薄、承载层要厚"回头看，他的拆分是：

- **入口统一成消息。** @ 它、回复、私聊、定时任务、群事件都转成同一种消息进同一个 Agent loop——不再为每种入口写一套逻辑，也不用关键词和指令菜单做意图路由；
- **要不要说话交给模型判断，但外面加确定性的上限。** 它可以选不回或只回一个表情；但每分钟最多发几条、对同一个人的冷却时间、深夜静默，由程序管；
- **人设写短。** 一段简短人设 + 少量典型例子；群里的梗和常用说法放进文件按需查，不在提示词里堆几十条规则；
- **记忆文件化、分层。** 群规和核心事实常驻；成员情况和按日期的记录按需查；临时笔记自动过期；
- **治理要加厚。** 管理操作走白名单和二次确认，群消息全部当不可信输入，所有操作留记录。

放到更一般的 Agent 产品上，他坚持五条：

1. **从最强的模型、最短的提示、最少的工具开始。** 先跑通，再按真实的失败往上加东西；
2. **每块补偿层都写清楚过期条件。** 它在补偿模型的哪一项短板，哪一条 eval 能证明它不再需要；
3. **新模型发布时，裸跑一遍。** 同一套 eval，一遍用完整配置、一遍只留人设和最基础工具。裸跑不输的那些规则和 skills，直接删掉；顺便用 Peak Ji 的指标看强模型带来的提升有多大；
4. **工具少而基础。** 发消息、搜索、读写文件、shell；某一类调用占了大头，再把它做成专用工具；
5. **把力气花在承载层。** 对 bot 来说就是群里积累的知识和成员记忆、QQ 生态的接入和治理、一套从真实群聊整理出来的评测集——这些都是下一代模型冲不掉的。

## 写在最后

这大概是「跟着 Joye 学 Agent」系列里最"架构向"的一篇。上一篇讲 Agent 比赛评审（为什么不用 Claude Code、Hook 到 Harness 从轻到重），这一篇把判断框架补完整了：**分清楚哪些东西是在补偿今天的模型，哪些是下一代模型也冲不掉的——前者随时准备删，后者每天都在加厚。**

我自己记下的几条：

- "删掉产品"删的是**补偿层**（替模型做判断的 UI 和规则），**承载层**（数据、评测、权限、集成、分发、成本）反而要加厚——判断标准是：**产品能不能在模型变强时免费变好**；
- 可直接用的检验指标：同一模型家族弱换强，架构能多拿多少提升；换不同家族模型表现差距尽量小；
- "今天的模型是最差的"——所以每块补偿层都写清过期条件，新模型发布时裸跑一遍（完整配置 vs 只留人设和最基础工具），不输的就删；
- 与上一篇呼应：上篇的"能用 Hook 解决的先别做 Harness"就是这个原则的雏形，这篇给了完整的判断框架和 Vercel d0（17 个工具删到 2 个，成功率 80%→100%）的实证；
- 规模要打折看：大团队的基础设施做法（预热缓存、按需唤醒虚拟机、分层记忆）个人照搬扛不住，原则通用、加厚程度看自己规模。
